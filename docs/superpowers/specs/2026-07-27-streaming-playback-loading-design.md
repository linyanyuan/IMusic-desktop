# Windows 流式播放与加载状态修复设计

## 背景

当前桌面端在 B 站播放地址带请求头时，会先调用 `AudioCacheService.getOrDownload` 下载完整音频文件，完成后才向播放器设置音源。首次播放一个约十几 MB 的音频时，用户会等待数秒甚至更久。移动端使用 `just_audio` 携带请求头直接播放远程地址，播放器可在缓冲到足够数据后开始播放，不等待完整下载。

上一轮优化已经在歌曲点击后写入 `loading` 状态并停止旧播放器，但播放栏仅根据当前歌曲状态渲染一条 3px 的动画轨道。首次进入软件时以及播放器尚无旧歌曲时，这个状态的可见性没有被有效验证。现有测试只确认动画 Widget 存在，没有确认它具有可见尺寸或随时间移动。

桌面端的元数据歌曲选源还存在一项与移动端不同的优化：只要搜索缓存中有歌曲标题，就跳过元数据详情查询，直接搜索 B 站候选。搜索列表标题并不能证明播放标识已经解析完成，这会降低候选准确性。当前候选评分也没有排除“伴奏”“off vocal”等无人声版本。

## 目标

1. 用户点击任意歌曲后立即停止当前音频，并立即进入可见的 `loading` 状态，包括软件启动后的第一次点击。
2. Windows 对未缓存的带请求头音频采用流式播放，不再等待完整文件下载。
3. 播放器确认开始播放时取消 `loading`；失败、取消或被更新请求替代时正确结束旧请求，不污染当前歌曲状态。
4. 恢复以歌曲详情和稳定 `playbackId` 为基础的选源顺序，降低选中伴奏或无人声版本的概率。
5. 已有本地缓存继续可用，不破坏现有缓存命中播放。

## 非目标

- 本次不实现完整的离线下载管理界面。
- 本次不在首次流式播放时并行下载第二份完整音频，避免重复流量。
- 本次不修改搜索结果、歌单渐进补全或曲库写入协议。
- 本次不重构与播放启动无关的播放器 UI。

## 方案选择

### 采用：`just_audio` + Windows `media_kit` 后端

桌面播放器改用 `just_audio`，Windows 通过兼容的 `media_kit` 后端解码和播放。远程音源直接携带 B 站要求的请求头交给播放器；已有缓存文件仍作为本地音源播放。

选择该方案的原因：

- 行为与移动端的流式播放路径一致。
- 播放器负责缓冲、Range 请求、暂停和 seek，不在应用内重复实现媒体代理协议。
- 能从根因上消除“完整下载结束后才开播”的等待。

### 未采用：为 `audioplayers` 增加本地 HTTP 代理

代理可以为现有播放器注入请求头，但应用需要自行管理端口、Range、取消、并发、资源释放和网络安全边界。实现和维护成本高于更换播放后端。

### 未采用：保留完整下载，仅修复选源与动画

该方案改动最小，但未缓存歌曲仍会等待完整下载，不能满足首次播放响应目标。

## 详细设计

### 1. 播放状态机

所有歌曲入口继续统一调用 `startSongPlayback`。一次点击按以下顺序执行：

1. 递增播放请求序号，使更早的异步播放请求失效。
2. 立即把点击歌曲设为当前歌曲并写入 `status: loading`。
3. 立即停止播放器中的当前音频。播放器此前是否有音源不影响第 2 步，因此首次点击同样展示加载状态。
4. 解析稳定播放标识和播放地址。
5. 缓存命中时设置本地文件音源；未命中时设置带请求头的远程流式音源。
6. 启动播放，并等待播放器发出当前音源同时满足 `playing == true && processingState == ready` 的事实状态。
7. 仅当本次请求仍是最新请求时，把当前歌曲状态改为 `playing`，加载动画随即取消。

`play()` 和 `setAudioSource` 的 Future 完成都只表示命令已被播放器接受，不等于已经开始出声，因此不能据此提前取消 `loading`。`just_audio` 的 `playing == true` 也只表示播放意图；只有当前音源同时满足 `playing == true && processingState == ready` 才进入 `playing`。缓冲期间 UI 必须继续显示不确定进度条。

播放地址解析、设置音源或启动播放失败时，最新请求进入 `error` 并结束加载动画。旧请求失败或晚到的播放器事件不得修改新请求的状态。用户快速连续点击时，只有最后一次点击有权设置音源、启动播放和更新 UI。

暂停、恢复、seek 和播放结束延续现有语义。状态转换定义如下：

| 触发条件 | 当前歌曲状态 | UI 行为 |
| --- | --- | --- |
| 用户点击歌曲，正在解析或设置音源 | `loading` | 显示不确定进度条，禁用 seek |
| 当前 generation 为 `loading` 或 `buffering`，尚未首次 ready | `loading` | 继续显示不确定进度条 |
| 当前 generation 为 `playing == true && ready` | `playing` | 取消 loading，显示确定进度 |
| 已开始播放后，`playing == true && buffering/loading` | `loading` | 重新显示不确定进度条；ready 后恢复 `playing` |
| 用户明确暂停，`playing == false` | `paused` | 即使底层仍收尾 buffering，也不自动改回 `loading` |
| 当前 generation `completed` | 沿用现有完成/下一首语义 | 只有当前 generation 可以触发自动下一首 |
| 当前 generation 报错 | `error` | 取消 loading，显示失败状态 |

恢复播放后，如果播放器需要缓冲，则先进入 `loading`；满足 `playing == true && ready` 后再进入 `playing`。

### 2. 播放器适配边界

播放业务逻辑不直接依赖第三方播放器类，而是通过播放器适配边界完成以下能力：

- `stop`
- 设置本地文件音源
- 设置带 HTTP 请求头的远程音源
- `play`、`pause`、`seek`
- `setVolume`
- 当前播放意图与 processing 状态查询
- 播放位置、总时长、完成、错误、processing/buffering 状态流
- 取消事件订阅和 `dispose`

适配层内部使用 `just_audio`，Windows 初始化兼容的 `media_kit` 后端。每次实际设置新音源都会创建一个带递增 `generation` 的 source session；该 session 独占其后端播放器实例和事件订阅。替换音源时，适配器先把新 generation 标为期望会话，停止并注销旧 session，再创建新 session。旧 session 的每个 position、duration、processing、completed 和 error 事件都携带旧 generation，业务层只接受当前 generation。这样旧音源迟到的事件不能触发新歌曲状态变化或自动下一首。

音源替换操作通过单一串行队列执行。任务真正设置音源前再次检查 generation；已经过期的任务直接结束，不创建播放器。适配器只允许一个当前 session，旧 session 停止并释放后才激活新 session。`play()` Future 只表示命令调用完成，业务层仍以带 generation 的组合状态事件判断是否真正开始播放。

点击新歌曲并废弃旧 generation 时，旧 session 中等待 `ready`、播放开始或音源设置的 Future 必须以明确的取消结果结束，不能一直悬挂到超时。创建新 session 后，在设置音源前重新应用业务层保存的当前音量，确保静音和音量设置不会因切歌恢复默认值。

迁移覆盖现有音量、静音、暂停、恢复、seek、播放位置、总时长、完成后自动下一首和资源释放能力，不增加均衡器、播放速度等新功能。测试替身继续在适配边界记录调用、generation 和异步时序，避免测试依赖真实媒体后端。

### 3. 缓存策略

- 为 `AudioCacheService` 增加只读缓存查询：只有目标文件存在且长度大于 0 时返回本地路径，不触发下载。播放前先执行该查询；命中则直接播放本地文件。
- 未命中时直接流式播放远程 URL，不再调用会阻塞开播的 `getOrDownload`。
- 本次不另起后台完整下载，以免同一首歌产生两次网络传输。
- 现有缓存文件格式和缓存清理逻辑保持不变；本次迁移不会主动删除用户缓存。
- 只有当前 generation 的本地缓存音源在“打开文件或解码本地文件”阶段明确失败时，才使该缓存失效，并最多回退一次对应远程流。网络错误、请求头错误或普通播放器错误不得删除缓存。

这一策略优先保证点击后的开播速度。未来如需“边播边缓存”或离线下载，应作为独立功能设计，并验证 Range 请求、部分文件和缓存完整性后再接入。

### 4. 选源顺序与候选过滤

`HybridMusicProvider.getPlayUrl` 使用以下顺序：

1. 歌曲已有稳定的 B 站 `playbackId` 时直接复用。
2. 没有 `playbackId` 时获取元数据歌曲详情，并与搜索缓存合并。
3. 详情返回 `playbackId` 时使用该标识。
4. 只有详情仍未提供播放标识时，才根据标题、艺人和时长搜索 B 站候选。

搜索结果中“已有标题”不能再作为跳过详情查询的条件。

候选选择把特征分为两类：

- 无人声硬排除：`伴奏`、`纯音乐`、`背景音乐`、`BGM`、`instrumental`、`karaoke`、`off vocal`、`无人声`、`消音`。目标歌曲标题本身不包含这些含义时，命中任一特征的候选直接排除，而不是仅降权；如果仅剩这类候选，则按现有“没有匹配音源”路径失败，不能播放错误版本。
- 可能仍有人声的软降权：`dance practice`、`练习室`、`live`、`现场`、`翻唱`、`cover`。这些候选保留，但低于同等匹配度的原唱/官方版本。

如果目标歌曲标题本身明确包含相同的无人声特征，则允许对应候选参与评分，避免纯音乐作品被错误过滤。规则不凭空构造播放地址。

### 5. 不确定进度条

`DesktopPlayerBar` 在当前歌曲为 `loading`，或当前播放请求对应的播放器处于阻断式 buffering 时，显示不确定进度条：

- 轨道保持全宽，固定高度 4–5px，不因动画或内容变化改变播放栏布局。
- 强调色片段沿轨道持续移动，背景轨道与片段具有足够对比度。
- 加载期间不显示确定进度圆点，并禁用 seek。
- 播放器确认 `playing` 后立即恢复确定进度条。
- `error`、请求取消或当前歌曲被替换时停止对应旧动画；若新歌曲仍在加载，动画保持连续。

动画不能依赖是否存在上一首歌曲、是否已有播放时长或播放位置，因此应用首次启动后的第一次点击也会出现。

## 错误与并发处理

- 播放请求序号仍是业务层唯一的“最后点击生效”仲裁依据。
- 播放器状态事件必须携带 source generation；旧音源迟到的 `playing`、`buffering`、`completed` 或错误事件不能覆盖新歌曲状态或触发自动下一首。
- B 站远程音源只使用 provider 返回的 URL 和固定允许的请求头，不接受 UI 提供任意请求头，也不开放通用代理能力。
- 流式音源失败时进入现有错误状态并向用户显示失败信息，不回退到阻塞式完整下载。
- 当前 generation 的本地缓存文件打开/解码失败时使该条缓存失效，并最多尝试一次远程流式播放；不循环重试同一损坏文件。
- `just_audio_media_kit` 对自定义请求头的公开能力说明为 supported but untested，因此它是实施前置风险。必须先在 Windows Release、对应歌曲缓存未命中的条件下，验证真实 B 站 URL 能携带 `Referer` 和 `User-Agent` 流式播放。验证失败就停止迁移并重新评估后端或代理方案，不能静默退回完整下载。

## 测试策略

### 状态与并发

- 应用初始没有当前歌曲时，点击后下一帧出现 `loading` 和不确定进度条。
- 已有歌曲播放时，点击新歌曲先调用 `stop`，并在 resolver 未完成期间保持 `loading`。
- 设置音源完成但播放器仍在 buffering 时继续显示 `loading`；收到当前音源 `playing` 后才切换为 `playing`。
- 连续点击两首歌时，第一首的迟到事件不能取消第二首的加载状态或启动第一首。
- 第一首迟到的 completed 事件不能跳过第二首或触发自动下一首。
- 最新请求失败时进入 `error`；过期请求失败不能影响当前歌曲。

### 流式播放与缓存

- 缓存命中时设置本地文件音源，不发远程播放请求。
- 缓存未命中时立即设置带请求头的远程音源，不等待 `getOrDownload`。
- 远程音源正确传递 `Referer` 和 `User-Agent`。
- 本地缓存打开/解码失败时仅失效该缓存并回退远程一次；其他错误不删除缓存。
- Windows 播放器适配层的 pause、resume、seek、setVolume、position、duration、completion、error 和 dispose 行为符合现有调用契约。
- 实施第一阶段使用 Windows Release 和明确未命中的缓存键验证真实 B 站请求头流式播放；该门禁通过后才进行完整适配迁移。

### 选源准确性

- 搜索缓存只有标题、没有 `playbackId` 时，必须先获取歌曲详情。
- 详情已有 `playbackId` 时不再执行 B 站候选搜索。
- 普通目标歌曲会硬排除伴奏、off vocal 候选；仅有无人声候选时返回无匹配音源。
- 目标标题本身为 instrumental/纯音乐时允许对应候选。
- 同等标题和时长下，原唱/官方候选的分数高于练习室、现场或翻唱候选。

### 视觉验证

- Widget 测试确认加载轨道宽度非零且高度不少于 4px。
- `pump` 动画时间后，移动片段的位置发生变化。
- 首次点击、切歌加载和 buffering 三种状态都显示动画，开始播放后动画消失。
- Windows Release 构建后手动验证搜索 `AOA` 并点击歌曲，观察开播时间、加载动画和人声版本。

## 验收标准

1. 任何歌曲点击后，旧音频立即停止，下一帧出现清晰可见的不确定进度条。
2. 在播放地址解析和播放器缓冲期间持续保持 `loading`；确认开始播放时取消 `loading`。
3. 未缓存的 B 站歌曲以带请求头的远程流式音源启动，不等待完整文件下载。
4. 已缓存歌曲继续从本地文件播放，已有缓存不被删除。
5. 元数据搜索结果缺少 `playbackId` 时先获取详情，候选搜索不会优先选择明显的伴奏或无人声版本。
6. 快速连续点击不会串歌，也不会由旧请求错误地取消新歌曲的加载动画。
7. 旧 generation 的 completed/error 事件不会触发当前歌曲状态变化或自动下一首。
8. Windows Release 在缓存未命中时完成真实 B 站带请求头流式播放验证。
9. 新增定向测试、现有播放测试和 Windows Release 构建通过；不引入新的静态分析错误。
