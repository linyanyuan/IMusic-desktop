# 搜索、播放与歌单交互响应优化设计

## 背景

当前搜索结果点击播放的关键路径包含多段串行网络工作：元数据歌曲需要反查 B 站版本，B 站播放源需要查询分P和字幕，再查询播放地址；Windows 端还需要在首次播放时把带请求头的音频完整缓存到本地。旧歌曲播放期间，新歌曲的加载状态又被延迟到播放地址解析完成后才展示，因此用户会感觉点击无响应。

搜索页的歌单结果来自 B 站搜索接口。初始结果包含标题、作者、时长和基础集合判断，但不包含准确分P数量。右键添加歌曲到歌单时，当前实现会先执行完整播放地址解析，再更新本地曲库并保存远端曲库，造成不必要的等待。

## 目标

1. 点击搜索结果或歌单详情中的歌曲后立即停止当前播放。
2. 新歌曲从点击开始立即进入加载状态，底部播放进度条显示不确定动画。
3. 缩短播放前的串行网络路径，同时保留现有 Windows 音频缓存兼容性。
4. 歌单搜索结果立即出现，后台补齐准确的分P数量和集合类型。
5. 移除没有有效结果的艺人 Tab。
6. 右键添加到歌单后立即给出界面反馈，并避免为收藏操作解析字幕和真实音频地址。

## 非目标

- 本次不迁移 `audioplayers`，也不新增本地流媒体代理。
- 本次不改变首次播放需要完整缓存带请求头音频的 Windows 兼容逻辑。
- 本次不修改后端曲库协议。
- 本次不扩展新的搜索类型或歌单管理功能。

## 设计

### 1. 播放启动流程

`startSongPlayback` 在接收到点击后按以下顺序执行：

1. 递增播放请求序号，使旧的异步请求失效。
2. 立即写入新队列、索引和当前歌曲，并将歌曲状态设为 `loading`。
3. 立即停止播放器中的旧歌曲。
4. 解析新歌曲的播放标识和播放地址。
5. 如播放地址需要请求头，继续使用现有稳定文件缓存；缓存完成后设置音源并播放。
6. 播放成功后把状态改为 `playing`；任何失败把状态改为 `error`。

较新的请求始终拥有状态更新权。较旧请求即使稍后完成，也不能覆盖当前歌曲或关闭当前加载状态。

#### 缩短关键路径

- `BilibiliMusicProvider.getPlayUrl` 只负责分P/CID和播放地址，不再等待字幕请求。
- 歌词统一在播放器成功启动后通过现有 `loadLyricsForCurrentSong` 异步加载。
- 元数据歌曲优先使用 `HybridMusicProvider` 已缓存的搜索结果进行 B 站匹配。缓存中已有标题和艺人时，不在播放前额外请求元数据详情。
- 已存在稳定 `playbackId` 的歌曲直接复用该标识。
- 已知 B 站分P元数据时优先复用，避免重复查询相同信息；没有已知数据时保持现有降级请求。

首次播放仍可能受完整音频下载时间影响，但点击反馈、字幕请求和冗余元数据请求不再增加这段等待。

### 2. 不确定进度条

`DesktopPlayerBar` 根据 `currentSong.status == 'loading'` 决定进度条模式：

- `loading`：显示沿轨道循环移动的不确定进度动画，不显示拖动圆点，禁用点击和拖动跳转。
- `playing` 或 `paused`：恢复现有确定进度显示和拖动行为。
- `error` 或无歌曲：显示空的静态轨道。

动画沿用当前进度条高度和主题强调色，不改变播放栏尺寸，避免布局跳动。Widget 销毁时释放动画控制器。

### 3. 歌单结果渐进补全

搜索接口返回后立即把结果写入 `searchResultsProvider`，不等待分P查询。歌单行初始展示：

- 普通候选：`作者 · 正在获取曲目数...`
- 已能根据标题和时长判断的长音频集合：`作者 · 歌曲集合 · 1:25:30`
- 标题中已解析出多个歌曲名：可立即展示估算歌曲数，但仍在后台确认是否为分P合集。

随后对当前搜索请求中的歌单结果执行后台补全：

- 最多同时发起 4 个 B 站分P查询。
- 查询到多个分P时，行内更新为 `作者 · 12 首歌曲 · 分P合集`。
- 只有一个分P且属于长音频集合时，保持 `作者 · 歌曲集合 · 1:25:30`。
- 查询失败时降级为 `作者 · 歌曲集合`，不显示弹窗，也不移除结果。

补全只替换对应结果的辅助字段，不改变列表顺序、滚动位置或可点击性。用户可以在补全完成前进入歌单详情。每次补全都检查搜索请求 ID；旧搜索的返回结果不能写入新搜索。

服务边界上，为 `MusicProvider` 增加带默认空实现的轻量曲目数量查询能力。B 站 provider 只调用分P列表接口，`HybridMusicProvider` 负责转发，`MusicService` 向 UI 提供统一入口。该能力不加载歌单详情、字幕或播放地址。

### 4. 移除艺人 Tab

- `SearchTab` 只保留 `all`、`songs` 和 `playlists`。
- 删除艺人标签及其分支映射。
- 综合搜索仍可接收后端返回的其他类型，但页面只展示歌曲和歌单。

### 5. 右键添加到歌单

添加流程改为本地优先、后台补全：

1. 用户选择目标歌单后，菜单立即关闭。
2. 立即把歌曲加入本地 `LibraryState`，使重新打开菜单时马上显示“已添加”。
3. 立即显示“正在添加到歌单...”反馈。
4. 后台只解析稳定 `playbackId`，不查询字幕、不请求真实音频 URL、不下载音频。
5. 用补全后的歌曲替换本地歌单中的对应条目。
6. 携带补全后的数据执行一次 `PUT /library`。
7. 保存成功显示“已添加到歌单”；保存失败恢复操作前的歌单状态并显示“添加失败”。

稳定播放标识解析由 `MusicService` 提供独立入口：

- B 站歌曲从自身 ID 规范化得到 `playbackId`，不发网络请求。
- 元数据歌曲先复用缓存中的 `playbackId`；没有时只执行 B 站匹配搜索。
- 解析失败时保留原歌曲数据，延续当前可保存但可能稍后再补全的降级行为。

该流程同时适用于搜索结果和歌单详情的右键菜单。已经存在于目标歌单的歌曲仍保持禁用状态，不重复保存。

## 错误与并发处理

- 播放请求由现有序号机制仲裁，最后一次点击生效。
- 搜索补全由搜索请求 ID 仲裁，旧查询不得更新新结果。
- 歌单添加在远端保存失败时完整回滚到操作前快照。
- 分P补全失败只影响辅助文案，不影响进入详情或播放。
- 所有新增网络请求只接受内部生成的 B 站标识，不接受任意远端 URL；不扩大现有网络信任边界。

## 测试策略

### 播放

- 使用延迟的播放地址 resolver，验证点击后旧播放器立即收到 `stop`。
- resolver 完成前，新歌曲状态必须为 `loading`。
- 新请求覆盖旧请求时，旧请求不能清除加载态或启动旧歌曲。
- B 站播放地址解析不等待字幕 Future。
- 元数据搜索缓存足够时，播放解析不额外请求元数据详情。
- 进度条在加载状态显示不确定动画并禁用 seek，播放后恢复确定进度。

### 歌单搜索

- 搜索主请求完成后，歌单行在分P Future 未完成时已经可见。
- 多分P结果更新为准确歌曲数量和“分P合集”。
- 单分P长音频显示“歌曲集合”和时长。
- 旧搜索的补全结果不能覆盖新搜索。
- 页面不再出现艺人 Tab。

### 添加到歌单

- 使用未完成的播放标识 resolver，验证本地歌单在 resolver 完成前已经更新。
- 解析完成后只保存一次远端曲库，保存数据包含稳定 `playbackId`。
- 验证收藏解析不会请求真实音频 URL或字幕。
- 远端保存失败时本地状态回滚。
- 搜索页和歌单详情页都立即显示进行中反馈，并在完成后显示最终结果。

## 验收标准

1. 点击任意新歌曲后，旧歌曲立即停止，进度条在下一帧进入不确定动画。
2. 歌词和字幕请求不再阻塞音频地址解析与播放启动。
3. 搜索歌单结果不等待分P接口即可展示；后台补全不会改变列表顺序。
4. 多分P和单个长音频集合具有明确、不同的辅助文案。
5. 搜索页仅保留综合、歌曲、歌单三个 Tab。
6. 右键添加歌曲后，本地歌单和进行中反馈立即更新；远端失败能够回滚。
7. 新增定向测试通过；除仓库已知的旧测试基线问题外，不引入新的测试失败或静态分析错误。
